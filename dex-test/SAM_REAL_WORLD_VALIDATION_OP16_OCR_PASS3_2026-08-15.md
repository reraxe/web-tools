## Optimization strategy

Pass 2 always launched twelve Tesseract processes: three lower-right regions,
two deterministic preprocessing variants, and two page-segmentation modes. Pass
3 retains that entire bounded set but schedules it:

1. **Fast primary:** lower-right primary, grayscale/autocontrast/sharpen, `PSM 11`.
2. **Independent confirmation:** the same bounded primary region with binary
   threshold preprocessing, `PSM 11`.
3. **Escalation:** bottom-band grayscale `PSM 11`, then its independent `PSM 7`
   read.
4. **Complete fallback:** the remaining eight Pass 2 combinations if a stable
   result still does not exist.

Early exit requires two valid agreeing reads and no other valid OCR candidate.
A first string that merely resembles a card number is insufficient. Any valid
disagreement disables early exit, and the complete twelve-attempt pipeline runs
before the unchanged consensus test is applied. OCR/visual and
reference/provider checks still occur independently after OCR.

No Pass 2 attempt was deleted. Eight low-yield attempts are deferred on clean
scans, while difficult scans may still use them.

## Tesseract and preprocessing changes

- Tesseract remains one local subprocess per attempted recipe. No persistent
  engine, shared mutable OCR state, external provider, or replacement engine was
  introduced.
- Crop preparation and PNG serialization are lazy. Unvisited regions and
  preprocessing variants are not created.
- A prepared crop is reused when escalation changes only page segmentation.
- Original scans remain unchanged and derived crops remain temporary.
- Recognition idempotency now includes the OCR method version so a changed OCR
  implementation cannot silently replay evidence generated by an older method.

Measured process execution dominated each attempt at approximately 158–183 ms.
The safe improvement therefore comes from reducing process launches, not from
weakening recognition or introducing shared Tesseract state.

## Asynchronous-readiness assessment

Recognition is still invoked synchronously by the current HTTP mutation, so the
request waits for OCR. No worker or queue was added. The service itself is ready
for a later queue boundary: each recognition has a deterministic idempotency key,
uses an isolated temporary directory, launches independent subprocesses, writes
one auditable recognition job, and has no shared OCR engine state. A future
`scan → enqueue → continue scanning` design could call this same service, but
would require separately approved durable job claiming, retries, progress, and
operator-visible failure handling.

## Recommendations and limits

- The initial sub-1,000 ms target and 500–800 ms stretch target were met on this
  exact controlled set without a safety regression.
- Keep the present thresholds and staged order unchanged pending a broader,
  separately approved physical-scanner validation set.
- Do not infer broad all-set accuracy from five OP16 scans.
- A persistent OCR engine or background worker might reduce latency further but
  would introduce concurrency and lifecycle risks outside this pass.
- No threshold tuning, reference-library expansion, Janna work, schema change,
  production deployment, or new feature phase is authorized by this result.
